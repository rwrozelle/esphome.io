The CoAP Server component exposes ESPHome entities (sensors, switches, binary sensors, buttons, text sensors, numbers,
locks, and valves) as [CoAP](https://coap.technology/) resources over a [Thread](https://www.threadgroup.org) network.
Clients can read entity states, subscribe to state changes via CoAP Observe (RFC 7641), and send commands.
Payloads use [CBOR](https://cbor.io/) encoding (SenML format, RFC 8428) for compact representation.

Optionally, [OSCORE](https://www.rfc-editor.org/rfc/rfc8613) (RFC 8613) security can be enabled to encrypt and
authenticate CoAP messages.

<Image src="/images/coap_server.png" alt="CoAP Server" layout="constrained" />

> [!NOTE]
> This component requires an ESP32 with an IEEE 802.15.4 radio (ESP32-C5, ESP32-C6, or ESP32-H2) and the
> [OpenThread](/components/openthread/) component.

```yaml
# Minimal configuration
coap_server:
```

## Configuration Variables

- **id** (*Optional*, [ID](/guides/configuration-types#config-id)): Manually specify the ID used for code generation.
- **port** (*Optional*, int): UDP port the CoAP server listens on. Defaults to `5683`.
- **max_connections** (*Optional*, int): Maximum number of simultaneous active client connections tracked for CoAP
  Observe. Range `1` to `5`. Defaults to `1`. Additional clients can still perform non-observe requests beyond this
  limit.
- **subscription_confirm** (*Optional*, boolean): Selects the CoAP Observe mode. When `false` (NON mode), clients
  send Non-Confirmable observe requests and liveness is tracked via a mutual ping mechanism. When `true` (CON mode),
  clients send Confirmable observe requests and liveness is tracked via CON acknowledgements. The two modes use
  different configuration variables — ping options are only valid in NON mode, `observe_retry` is only valid in CON
  mode. Defaults to `false`.

### NON observe mode options (`subscription_confirm: false`)

These options are only valid when `subscription_confirm` is `false`. Setting any of them when
`subscription_confirm: true` is a configuration error.

- **server_ping_interval** (*Optional*, [Time](/guides/configuration-types#config-time)): How often the server expects
  clients to ping it. This value is sent to clients in the `/info` response so they know the expected ping frequency.
  Minimum `20s`. Defaults to `60s`.
- **server_ping_timeout_ratio** (*Optional*, float): Multiplier applied to `server_ping_interval` to compute the
  server-side timeout for a client ping. Must be a positive value. Timeout has a floor of 1 second. Defaults to `2.5`.
- **server_ping_retry** (*Optional*, int): Number of consecutive missed pings before a client connection is considered
  timed out. Range `1` to `5`. Defaults to `1`.
- **client_ping_interval** (*Optional*, [Time](/guides/configuration-types#config-time)): How often the server sends
  liveness pings to connected clients. Minimum `60s`. Defaults to `60s`.
- **client_ping_timeout_ratio** (*Optional*, float): Multiplier applied to `client_ping_interval` to compute the
  timeout waiting for a client ping response. Must be a positive value. Timeout has a floor of 1 second. Defaults to `2.5`.
- **client_ping_retry** (*Optional*, int): Number of consecutive missed pings before a client is considered
  disconnected. Range `1` to `5`. Defaults to `1`.

> [!NOTE]
> When the [OpenThread](/components/openthread/) device type is `MTD` with a configured `poll_period`, both
> `server_ping_interval` and `client_ping_interval` must be greater than or equal to the `poll_period`.

### CON observe mode options (`subscription_confirm: true`)

This option is only valid when `subscription_confirm` is `true`. Setting it when `subscription_confirm: false`
is a configuration error.

- **observe_retry** (*Optional*, int): Number of times a client should re-establish a broken observation before
  entering backoff reconnect. Retries use exponential backoff starting at 10 s, capping at 5 min. Once all retries
  are exhausted the device is marked unavailable and the client enters an exponential backoff reconnect loop until
  the device is reachable again. Set to `0` to skip retries and go directly to backoff reconnect on the first
  stream failure. Range `0` to `10`. Defaults to `1`.

### Automation and security

- **on_client_connected** (*Optional*, [Action](/automations/actions#all-actions)): Automation to run when a client
  establishes a connection. See [`on_client_connected` Trigger](#on_client_connected-trigger). Client tracking is IP
  only; the port is not used for tracking.
- **on_client_disconnected** (*Optional*, [Action](/automations/actions#all-actions)): Automation to run when a client
  connection is closed. See [`on_client_disconnected` Trigger](#on_client_disconnected-trigger).
- **oscore** (*Optional*): OSCORE security configuration. When present, all client requests (except
  `/.well-known/core` and `/info`) must include valid OSCORE credentials.

  - **master_secret** (**Required**, hex string): OSCORE Master Secret. Minimum 16 bytes (32 hex characters). Must be the same value on both the device and the client. Example: `"0102030405060708090a0b0c0d0e0f10"`.
  - **master_salt** (*Optional*, hex string): OSCORE Master Salt. Defaults to empty.
  - **sender_id** (**Required**, hex string): OSCORE Sender ID (non-empty hex, must differ from `recipient_id`).
  - **recipient_id** (**Required**, hex string): OSCORE Recipient ID (non-empty hex, must differ from `sender_id`).
  - **id_context** (*Optional*, hex string): OSCORE ID Context. Defaults to empty.

## Automation Triggers

<span id="on_client_connected-trigger"></span>

### `on_client_connected` Trigger

Activated each time a client establishes a connection. The variable `client_address` (`std::string`) contains the
IPv6 address of the connecting client.

```yaml
coap_server:
  on_client_connected:
    - logger.log:
        format: "CoAP client connected: %s"
        args: ["client_address.c_str()"]
```

<span id="on_client_disconnected-trigger"></span>

### `on_client_disconnected` Trigger

Activated each time a client connection is closed or timed out. The variable `client_address` (`std::string`)
contains the IPv6 address of the disconnected client.

```yaml
coap_server:
  on_client_disconnected:
    - logger.log:
        format: "CoAP client disconnected: %s"
        args: ["client_address.c_str()"]
```

## CoAP Resources

### Fixed Resources

| Path | Methods | OSCORE-exempt | Description |
|------|---------|---------------|-------------|
| `/.well-known/core` | GET | Yes | Standard CoAP resource discovery (RFC 6690). Lists all entity resources. |
| `/info` | GET | Yes | Device information: name, ESPHome version, build time, model, ping parameters, `subscription_confirm`, and `observe_retry`. |
| `/ping` | GET | No | Liveness check. Returns `{2: uptime_seconds}` or `{2: -1}` on first contact after reboot. |

### Entity Resources

Each entity is assigned a path of the form `/fp/{N}/g/1` where `N` is a sequential index starting at 1.
Indices are assigned in the following entity-type order, with entities of each type indexed in declaration order:

1. Binary sensors
2. Buttons
3. Locks
4. Numbers
5. Sensors
6. Switches
7. Text sensors
8. Valves
9. Logger (if the logger component is present)

The methods and payload for each entity type:

| Entity type | Path | Methods | Notes |
|-------------|------|---------|-------|
| Binary sensor | `/fp/{N}/g/1` | GET, OBSERVE | Read-only. Response: `{4: bool}` |
| Button | `/fp/{N}/g/1` | POST | Write-only. POST to press (empty or any payload). |
| Lock | `/fp/{N}/g/1` | GET, OBSERVE, POST | POST `{4: true}` to lock, `{4: false}` to unlock. |
| Number | `/fp/{N}/g/1` | GET, OBSERVE, POST | POST `{2: float}` to set value. |
| Sensor | `/fp/{N}/g/1` | GET, OBSERVE | Read-only. Response: `{2: float}` |
| Switch | `/fp/{N}/g/1` | GET, OBSERVE, POST | POST `{4: true}` to turn on, `{4: false}` to turn off. |
| Switch | `/fp/{N}/g/2` | POST | POST `{4: true}` to toggle. |
| Text sensor | `/fp/{N}/g/1` | GET, OBSERVE | Read-only. Response: `{3: string}` |
| Valve | `/fp/{N}/g/1` | GET, OBSERVE, POST | POST `{4: true}` to open, `{4: false}` to close. |
| Valve | `/fp/{N}/g/2` | POST | POST `{4: true}` to stop. |
| Logger | `/fp/{N}/g/1` | GET, OBSERVE | Read-only. Streams log entries as a CBOR array: `[millis, level, tag, message]`. |

Payloads use [CBOR](https://cbor.io/) map encoding with SenML keys: `2` = numeric value (`v`), `3` = string value (`vs`),
`4` = boolean value (`vb`).

To subscribe to state changes, send a GET with the CoAP Observe option set to `0`. To cancel, send a GET with
Observe set to `1`.

> [!NOTE]
> CoAP notifications are sent over UDP, which is best-effort and connectionless. An individual notification may be
> lost in transit — this is normal and by design. The next state change delivers the current value, so a missed
> notification is self-healing. No intermediate states are buffered or retried on the device. This is a deliberate
> trade-off: buffering would require heap allocation at runtime, which is avoided on embedded devices to prevent
> memory fragmentation and to allow the device to enter light sleep between updates.

## Examples

### Basic CoAP Server with a Sensor and Switch

```yaml
openthread:
  device_type: FTD

coap_server:
  port: 5683
  max_connections: 2

sensor:
  - platform: uptime
    name: "Uptime"

switch:
  - platform: gpio
    pin: GPIOXX
    name: "Relay"
```

### CoAP Server with CON Observe Mode

Use CON observe when you want the protocol to confirm delivery of every notification. Ping is not used;
`observe_retry` controls how many times the client re-establishes a broken observation before entering
backoff reconnect. mDNS re-announcements are ignored in CON mode.

:::caution[Reboot detection requires regular updates]
In CON mode the client detects a reboot only when a CON notification is sent and goes unacknowledged.
Entities that rarely change (e.g. a switch held in one state) will not trigger detection. Always include
at least one regularly-updating entity — such as an uptime sensor — so reboots are caught within one
update cycle.
:::

```yaml
coap_server:
  subscription_confirm: true
  observe_retry: 2          # Re-subscribe up to 2 times, then enter backoff reconnect
  max_connections: 2
```

### CoAP Server with OSCORE Security

```yaml
coap_server:
  oscore:
    master_secret: "0102030405060708090a0b0c0d0e0f10"
    sender_id: "01"
    recipient_id: "02"
```

### CoAP Server with Connection Logging

```yaml
coap_server:
  max_connections: 3
  on_client_connected:
    - logger.log:
        format: "Client connected: %s"
        args: ["client_address.c_str()"]
  on_client_disconnected:
    - logger.log:
        format: "Client disconnected: %s"
        args: ["client_address.c_str()"]
```

## OSCORE Compliance Notes

The current OSCORE implementation deviates from RFC 8613 in three ways. These are pragmatic workarounds
required by OpenThread's CoAP routing architecture, not design choices. They are documented here so
anyone deploying this component understands the limitations and can track resolution.

### Violation 1 — URI-Path Sent in Plaintext

**What the spec says:** URI-Path is a Class E option in RFC 8613 §4.1.3.3. It must appear only inside
the encrypted inner message. The outer CoAP message should carry no URI-Path.

**What we do:** URI-Path must be present on the outer (unencrypted) message so OpenThread can route the
request to the correct resource handler before any application-level decryption occurs. Clients must
copy the URI-Path back onto the outer protected message after OSCORE encrypt.

**Security implication:** A network observer can see which resource path is being accessed (e.g.,
`/fp/3/g/1`). Entity paths are opaque sequential indices, not descriptive names, so this leaks which
entity is being targeted but not its type, name, or value. All payload content remains encrypted.

**Resolution:** Requires a pre-dispatch hook in OpenThread's CoAP API so the server can receive all
inbound packets before resource matching, decrypt, and re-dispatch by inner URI-Path. A feature request
has been filed at [openthread/openthread#13234](https://github.com/openthread/openthread/issues/13234).

### Violation 2 — FETCH Remapped to POST on Outer Message

**What the spec says:** An OSCORE-protected CoAP Observe subscribe request should have an outer code of
FETCH (RFC 8132, code 0.05). The inner message carries the actual GET with Observe option.

**What we do:** OpenThread's `IsRequest()` only recognises codes GET through DELETE (0x01–0x04). A FETCH
outer code is silently dropped before reaching any handler. Clients must use POST (0x02) as the outer
code instead. The server detects the observe intent from the inner decrypted message.

**Security implication:** None. This is a protocol conformance issue only.

**Resolution:** Requires OpenThread to recognise FETCH as a valid request code. Tracked in
[openthread/openthread#12838](https://github.com/openthread/openthread/issues/12838).
Once that lands and the client is updated, the remap will be removed and the outer code will be FETCH
as the spec requires.

### Violation 3 — CON/NON Mode Detected from Outer Message Type

**What the spec says:** The inner decrypted message carries the authoritative message type. Subscription
mode (CON vs NON observe) should be determined from the inner type after decryption.

**What we do:** The server reads the outer message type before decryption to determine whether the
client is subscribing in CON or NON mode. Clients must set the correct CON/NON type on the outer
protected message to match the `subscription_confirm` setting.

**Security implication:** None. Message type is Class U (unprotected) in OSCORE — it is not encrypted
in any case.

**Resolution:** Follows from Violation 1. Once a pre-dispatch hook allows decrypt-before-route, the
server can read the inner message type instead. No separate upstream change is required.
